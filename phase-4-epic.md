# Epic: Phase 4 — Structured Import

**Parent:** [investment-tracker-prd.md](investment-tracker-prd.md) §17, Phase 4
**Design reference:** [dashboard.html](dashboard.html), [style-guide.md](style-guide.md)
**Owner:** J
**Status:** Not started
**Created:** 2026-09-24

---

## Epic goal

Load IBKR and Kraken activity from the CSV files each broker exports, so that most transactions never have to be typed. Every import is previewed before it commits. Rows the parser can't map are reported, never dropped. Importing the same file twice changes nothing.

## Why this phase now

PRD §8: prices can be backfilled months later, but transactions can't. The longer J types IBKR and Kraken activity by hand, the more likely a dividend or fee goes unrecorded. This phase moves two of three platforms and most of the transaction volume onto a deterministic path.

## In scope

PRD 10.5 in full. The IBKR Flex Query or activity statement CSV, and the Kraken ledger and trade history CSV. The privacy rule in PRD §12 that these files are parsed locally.

## Out of scope

BDO Securities statement OCR (P2). Any broker API or login. Scheduled imports.

## Definition of done

- A real month of IBKR and Kraken activity imports with no manual typing.
- Importing the same files a second time changes no figure on the dashboard (PRD §13).
- Cash balances on IBKR and Kraken after import match the brokers' statements for that month.
- Every row that didn't import is listed with a reason.

## Decisions (made 2026-09-24)

**Kraken staking and rewards are income at their value on receipt** (PRD §9). A reward adds the received quantity to the position, with a cost basis equal to its market value on the receipt date. It counts as income alongside dividends, and generates no cash leg. The rejected alternative, a quantity increase at zero cost, would push every reward into unrealised gain and distort average cost.

**Import has its own page** (PRD §10.5). It is not a tab in the Add dialog. The dialog's 620px width can't hold a multi-row preview with rejected rows and update diffs.

## User stories

### S1 — Reward transaction type

**As J, I want** staking rewards recorded as income at their value on receipt, **so that** they count as income and my average cost stays meaningful.

**Acceptance criteria**
- [ ] A migration adds `reward` to the transaction type constraint. SQLite can't alter a CHECK constraint, so this means a table rebuild, tested against a copy of a populated database.
- [ ] A reward stores quantity, unit value on the receipt date (from the stored price series), and the resulting cost basis. It generates no cash leg.
- [ ] Average cost after a reward is (previous cost + reward value) / (previous quantity + reward quantity). Verified by a hand-computed test.
- [ ] Rewards are queryable as income per instrument and per period, and are available to the Phase 3 income KPI.
- [ ] A reward can also be entered manually, from the Transaction tab of the Add dialog.
- [ ] The Kraken ledger row types that represent rewards are listed and documented.

**Size:** 3

---

### S2 — Import framework: upload, stage, preview, commit

**As J, I want** every import to show me what it will write before it writes it, **so that** a bad file never reaches the ledger.

**Acceptance criteria**
- [ ] A dedicated Import page (see S10), with a file picker and a platform selector. The format is auto-detected where possible.
- [ ] Parsing runs locally in the Flask process. The file never leaves the machine (PRD §12).
- [ ] Parsed rows go to a staging area, not to `transactions`.
- [ ] The preview shows rows read, rows to create, rows to update, rows unchanged, and rows rejected, following the style guide's preview pattern.
- [ ] Commit writes every staged row in one database transaction. A failure midway writes nothing.
- [ ] Imported rows get `source_type = 'import'` and `external_id` set to the broker's own id. The display source reads "import · IBKR Flex" or "import · Kraken CSV", as in the mockup's transaction list.
- [ ] The uploaded file is stored under a local path and recorded in `documents`, so an import can be traced back to its file.

**Size:** 5

---

### S3 — IBKR trades

**As J, I want** IBKR buys and sells imported from the Flex Query CSV, **so that** my US positions build themselves.

**Acceptance criteria**
- [ ] Buys and sells are mapped with trade date, quantity, price, commission, and currency.
- [ ] `external_id` uses IBKR's trade id.
- [ ] Commissions go into `fees`, so they land in cost basis on buys and reduce proceeds on sells, as Phase 1 does.
- [ ] Cash legs are generated by the ledger, as for manual trades (see S8).
- [ ] The required Flex Query sections and fields are documented, so the export can be set up once and reused.

**Size:** 5

---

### S4 — IBKR dividends, withholding tax, deposits, and fees

**As J, I want** IBKR dividends imported with their withholding tax as one dividend, **so that** the gross, tax, and net rule from Phase 1 still holds.

**Acceptance criteria**
- [ ] IBKR reports dividends and withholding tax as separate cash rows. The parser pairs them by instrument and pay date into one `dividend` transaction with gross, tax, and net.
- [ ] An unmatched withholding row is rejected with a reason, never imported alone.
- [ ] Withholding reversals and corrections (which IBKR issues) update the paired dividend instead of creating a second one.
- [ ] Deposits and withdrawals become external `transfer` transactions.
- [ ] Platform fees (data subscriptions and similar) become `fee` transactions.
- [ ] FX conversions inside IBKR (USD↔PHP cash) are imported as an internal pair and do not count as external flows.

**Size:** 3

---

### S5 — Kraken ledger and trades

**As J, I want** Kraken activity imported from its ledger CSV, **so that** my crypto positions and USD cash build themselves.

**Acceptance criteria**
- [ ] The two ledger rows that make up one trade (spend and receive, joined on `refid`) become one buy or sell.
- [ ] Trade fees are attached to the trade, not imported as separate fees.
- [ ] Deposits and withdrawals of USD become external transfers.
- [ ] Crypto deposits and withdrawals to an outside wallet are handled one of two ways, decided per case: as a transfer at market value, or rejected for manual handling. Never silently.
- [ ] Staking and reward rows become `reward` transactions (S1), valued at the stored close for their receipt date. A reward whose date has no stored price is rejected with that reason, not valued at zero.
- [ ] Stablecoins are either cash-equivalent instruments or ordinary crypto holdings. The choice is decided once and applied consistently.
- [ ] `external_id` uses Kraken's ledger id.

**Size:** 5

---

### S6 — Instrument mapping and rejected rows

**As J, I want** rows that don't match a known instrument or type shown as rejected, **so that** nothing disappears into a silent skip.

**Acceptance criteria**
- [ ] Rows are matched to instruments by the broker symbol stored on the instrument (from Phase 2 S1), not by display ticker.
- [ ] An unknown symbol is rejected with the symbol shown. J can create the instrument or map the symbol to an existing one from the preview, then re-run the preview.
- [ ] An unknown transaction type is rejected with the broker's raw type shown.
- [ ] Rejected rows are listed in the preview and in the import history, each with its raw values and a reason.
- [ ] Nothing commits while a row is in an unresolved state that J hasn't explicitly chosen to skip.

**Size:** 3

---

### S7 — Idempotent re-import and edits to imported rows

**As J, I want** re-importing an overlapping date range to update rather than duplicate, **so that** I can export generously without checking where the last export ended.

**Acceptance criteria**
- [ ] The unique index on `(platform, external_id)` from Phase 1 is the dedupe key.
- [ ] A re-imported row with identical values is counted as unchanged and not rewritten.
- [ ] A re-imported row with changed values (a broker correction) is shown in the preview as an update, with before and after values.
- [ ] Imported rows can't be edited field by field in the transaction form. They can be deleted, and a later re-import restores them. The form says why.
- [ ] A test imports the same file twice and asserts every dashboard figure is identical.
- [ ] A test imports two overlapping monthly files and asserts no duplicate rows.

**Size:** 3

---

### S8 — No double cash

**As J, I want** imported trades and dividends to move cash exactly once, **so that** platform cash matches the broker.

**Acceptance criteria**
- [ ] For trades and dividends, the ledger's generated cash leg is the only cash movement. The broker's own cash rows for those events are matched to the leg and not imported separately.
- [ ] After import, the computed cash balance per platform and currency is compared with the broker's ending cash for the file's period, when the file contains it. Any difference is shown in the preview.
- [ ] A non-zero difference doesn't block commit, but it is recorded with the import and shown until explained.

**Notes:** This is the import equivalent of the dividend double-count trap. Both brokers report the cash side of every trade. Importing those rows as well as generating legs doubles every cash movement.

**Size:** 3

---

### S9 — Import history

**As J, I want** a list of past imports, **so that** I can see what came from which file and undo a bad one.

**Acceptance criteria**
- [ ] Each import shows date, platform, file name, the period covered, and the created, updated, unchanged, and rejected counts.
- [ ] Each import links to the transactions it created and to the stored file.
- [ ] An import can be rolled back, which removes the transactions it created. Rollback is refused, with the conflict named, if a later sell depends on an imported buy (the same rule as Phase 1 S12).

**Size:** 2

---

### S10 — Import page and entry point

**As J, I want** import on its own page, reachable from the dashboard, **so that** it's part of the routine and the preview has room to show every row.

**Acceptance criteria**
- [ ] A full-width Import page, built from the style guide's card, table, badge, and preview components.
- [ ] An "Import file" `.btn` on the holdings card, next to "Record transaction", opens the page. The header keeps "Refresh all prices" as its only primary button.
- [ ] The page's layout: upload card, then summary counts, then a staged-rows table grouped by outcome (create, update, unchanged, rejected). Commit is the page's single primary button, labelled with the count ("Commit 42 rows").
- [ ] After commit, the toast states figures: "Imported 42 IBKR rows · 3 rejected · cash matches statement".
- [ ] Imported rows appear in Recent transactions with their import source label.

**Size:** 3

---

### S11 — Phase verification

**As J, I want** a real month of activity imported and checked, **so that** the phase is verified, not assumed.

**Acceptance criteria**
- [ ] One real month of IBKR and Kraken exports imported with no typing.
- [ ] The same files re-imported. No figure changes.
- [ ] Cash balances match both brokers' statements for the month.
- [ ] Any manual transactions for the same period, entered before this phase, are reconciled against the import and duplicates removed. The method is written down.
- [ ] Results added to [docs/reconciliation.md](docs/reconciliation.md).

**Notes:** The last criterion matters. Phases 1–3 were run on typed IBKR and Kraken history, which has no `external_id`. The first real import will duplicate it unless those rows are matched or retired first.

**Size:** 3

## Total: 11 stories, 38 points

## Prototype alignment

**Covered by the mockup:** only the source labels on transactions ("import · IBKR Flex", "import · Kraken CSV"). The mockup shows imported rows existing, but not how they get there.

**Not in the mockup and needs design before S2 and S10:**
- The Import screen: file picker, platform, and the preview with created, updated, unchanged, and rejected counts.
- The rejected-row list, with inline "create instrument" and "map to existing" actions.
- The update diff for broker corrections.
- The import history list and rollback.
- Navigation is decided: a separate page, opened from the holdings card (S10). Its layout still needs a mock before S2 starts.
- Staking rewards need a type chip (`reward`) in Recent transactions, and a Reward option in the Add dialog's transaction types (S1).

The style guide's preview and validation patterns (principle 4, §5 Forms) cover the interaction model. The screens themselves don't exist yet.

## Risks carried into this phase

- **Import duplication** (PRD §14). The dedupe key is in the schema. S7 tests it, and S11 handles duplication against typed history.
- **Double cash** (S8). This is quiet and flattering in the same way as dividend double-counting.
- **Broker format drift.** IBKR Flex columns are configurable, and Kraken has changed its CSV before. The parser has to fail loudly on unknown columns, never guess.
